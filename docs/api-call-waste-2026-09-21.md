# APIコールとエリア指定の無駄を洗い出した結果(2026-09-21)

「1. 無駄なAPI呼び出しを抑えられているか」「2. お店探索のエリア指定に無駄がないか」の
2点を、ドキュメントと実コードを突き合わせて確認した記録。**コードは変更していない**
(このドキュメントの追加と、下記で見つかった既存ドキュメントの誤りの訂正のみ)。

## 結論

- 一本化・排他制御・SKU分離といった**構造の作り込みは効いている**。意図せず二重に叩く経路は、
  探した限り本番経路には無い
- 最大の取りこぼしは、**3,370 Proコールをかけて得た調査結果を本番クロールが一切見ていない**こと。
  階層0だけで284 Enterpriseコール(無料枠の約28%)が、既に答えの分かっている問いに使われる
- `エラー` セルが恒久的に再コールされ続ける**確実なリーク**がある
- **`docs/current-status-2026-09-20.md` の「重複している検索範囲」の診断が間違っていた**。
  「大きいグループ(22〜23マス、6個)」は旧バグの名残ではなく、正方格子の構造的な東西重複。
  書かれている通りに「1つだけ残す」と、その行の店をほぼ全部取りこぼす(本書で訂正済み)

## 1. 無駄なAPIコールは抑えられているか

### 効いている抑制策

| 仕組み | 実装 |
|---|---|
| 1マス1コールへの一本化 | `lib/crawler/PlaceTypeSetCellSearch.js:34` — 追加コールなし |
| 多重実行の排他 | `entrypoints/crawlAllGrids.js:46-50` `LockService.tryLock(0)` |
| 未処理0件なら即終了 | `entrypoints/crawlAllGrids.js:129-135`(トリガー空振りのコスト0) |
| SKU別の月間ハードキャップ | `lib/api/PlacesApiClient.js:118` fetch直前にチェック |
| 429時の枠返却 | `lib/api/PlacesApiClient.js:85-96` `refundApiQuota` |
| 調査をPro枠へ隔離 | 調査系4本すべて `PLACE_SURVEY_FIELD_MASK` |
| 飽和時は4分割(5コール)でタイプ分割(11コール)を回避 | `entrypoints/crawlAllGrids.js:173-183` |
| `要確認(上限到達)` は完了扱い | `lib/grid/GridSchemaMigration.js:35-38` — 再コールされない |

Places API を叩くのは `lib/api/PlacesApiClient.js:153` の1箇所だけで、課金SKUは fieldMask から
導出される(`apiSkuOfFieldMask`)。呼び出し口が1つなので、上限チェックの抜け道も無い。

### 残っている無駄

#### (1) 調査結果が本番クロールに使われていない ← 最大

`crawlAllGrids` は「グリッド一覧」の処理状況しか見ず、`調査(マス)` / `調査(分割マス)` を
参照しない。`調査(マス)` には `グリッドID / 中心緯度 / 中心経度 / 半径m / 階層 / 取得件数`
(`entrypoints/surveyAllCells.js:172-174`)が揃っていて、そのまま種として使える状態にある。

結果、次の2種類のコールが「既に答えが分かっている問い」に使われる。

- **0件と分かっているマス**(階層0で64、全域で331)も、Enterprise で1コール叩いて
  「0件だった」ことを学び直す
- **飽和と分かっているマス**(階層0で220)も、まず親で Enterprise 1コール払ってから分割する。
  `spawnChildGrids` は座標だけを追記し、**親が取った Place ID 集合は子に渡らない**
  (`lib/grid/GridSubdivision.js:74-103`)。子4コールが同じ矩形を再走査して必ず取り直すので、
  この親コールは収穫としては無価値

階層0だけで 64 + 220 = **284 Enterpriseコール**。無料枠1,000/月に対して約28%、
3.4ヶ月ぶんに相当する。`docs/survey-findings-2026-09.md` 4-1「収穫ロジックの実装(本命)」が
まさにこれで、未着手のまま。

#### (2) `エラー` セルが無限にリトライされる ← 確実なリーク

`entrypoints/crawlAllGrids.js:185` が書く `'エラー'` は `GRID_DONE_STATUSES`
(`lib/grid/GridSchemaMigration.js:35-38`)に含まれていない。つまり次回実行で必ず再検索される。

一時的な障害なら正しい挙動だが、**恒久的に失敗する行が1つあると、日次トリガーのたびに
Enterprise枠が1ずつ溶け続ける**。しかもクォータ起因でないエラーは自前カウンタから
返却されない(`lib/api/PlacesApiClient.js:78-80` に「あえて数えたままにする」と意図が明記)。

リトライ回数を持つ列が無いため、一時障害と恒久障害をコード側で区別できない。

#### (3) 0件だったことをシートに残していない ← 未来の無駄を作っている

0件も1〜19件も同じ `'処理済み(プローブ)'` になる(`entrypoints/crawlAllGrids.js:187`)。
`placeTypeSetEmpty` フラグ(`lib/crawler/PlaceTypeSetCellSearch.js:80`)はログの集計値に
しか使われない。

旧方式用の `GRID_STATUS_EMPTY_BY_GROUP_A`(`lib/grid/GridSchemaMigration.js:33`)は、
**現在どこからも `setValue` されないデッドコード**になっている。`entrypoints/surveyEmptyCells.js:200`
の答え合わせはこの値を数えるので、今後 `crawlAllGrids` が処理する行に対しては常に0を返す。

つまり **Googleに1コール払って「ここは0件」という一番確実な情報を得ているのに、捨てている。**
(1)の改修で必要になるデータそのもの。

#### (4) 本番経路に1実行あたりの予算上限がない

`SURVEY_MAX_CALLS`(`lib/survey/SurveyCallBudget.js`)を読むのは調査系3本だけで、
`entrypoints/crawlAllGrids.js` には参照が1つもない。効くのは月間1,000のハードキャップと
4.5分の時間停止だけ。「今日は50コールだけ試す」という絞り方が現状できない。

#### (5) 飽和閾値 `20` が定数化されておらず4箇所に散っている

`lib/api/PlacesApiClient.js:131`(`maxResultCount`)/ `lib/crawler/PlaceTypeSetCellSearch.js:76` /
`lib/crawler/TypeGroupCellSearch.js:95,115` / `entrypoints/surveyAllCells.js:136`。

`MAX_TIER`・`CHILD_CELLS_PER_PARENT`・`INCLUDED_TYPES_MAX_PER_REQUEST` は定数化されているのに、
ここだけリテラル。ずれると「永久に分割し続ける」か「飽和を見逃す」のどちらかが起きる。

#### (6) `rankPreference` を指定していない(= POPULARITY)

`lib/api/PlacesApiClient.js:129-140` のペイロードに `rankPreference` が無い。既定の POPULARITY では
返る20件が円全体に散らばるため、後述する「隣のセルの店が20件枠を食う」問題をまともに受ける。

`DISTANCE` にすると「中心から近い順20件」になり、担当矩形の内側に収まりやすくなる。
`places.location` は既に取得済み(Pro段なので追加コスト0)なので、返った20件の最遠距離を
「飽和の強さ」の指標としても使える。

**ただし効果は未実測。** このリポジトリの「測ってから決める」方針(`docs/survey-next-actions-2026-09-20.md` 4章)に
合わせ、確定事項ではなく検証課題として扱う。

#### (7) 調査系のスキップ判定が本番の進捗を見ない

`surveyAllCells` / `surveySaturatedCells` / `comparePlaceTypeSetWithTypeGroups` は
自分の調査シートしか見ない。`entrypoints/surveyEmptyCells.js:99` だけが
`GRID_DONE_STATUSES` を参照して本番の探索済みセルを除外している。
Pro枠なので営業枠は食わないが、Pro枠を二重に消費しうる。

#### (8) `apiSkuOfFieldMask` が文字列の完全一致

`lib/api/PlaceSearchFieldMask.js:93` は `fieldMask === PLACE_SURVEY_FIELD_MASK` で判定する。
マスクを少しでも編集すると未知扱いになり Enterprise 枠を消費する。
同82-84に「未知は Enterprise 扱い＝小さいほうの枠で止まるほうが安全」と意図が書かれている通り
安全側ではあるが、**実際の課金はProなのに営業用の1,000枠だけを食う**ミスマッチは起こりうる。

### 無駄ではないと確認できたもの

- **ページネーション未使用** — Nearby Search (New) は pageToken 非対応なので原理的に不可
  (`docs/Overview.js` の「密集エリア対策」冒頭)
- **アプリレベルのリトライなし** — 無駄コールを生まない方向。ただし(2)の副作用がある
- **飽和セルの親子重複(1+4コール)** — 飽和判定に親コールが要るので原理的に不可避

APIコールではないが、`entrypoints/crawlAllGrids.js:177/181/185/187` のステータス書き込みが
1行ずつのラウンドトリップになっている。`lib/crawler/PlaceRowWriter.js:1-7` が
「`appendRow` の往復が実行時間を圧迫する主因だった」と書いたのと同じ問題がグリッド側に残っており、
6分制限内で進めるマス数に効く。

## 2. エリア指定の無駄と最適化余地

### (A) 「重複している検索範囲」の診断が間違っていた ← 要訂正

`docs/current-status-2026-09-20.md` は重複を**旧バグの名残**と説明していたが、数値が合わない。

`cellCoverRadiusMeters`(`lib/grid/GridGeometry.js:44-47`)はセル矩形の半対角を半径にする。
中心緯度35.855・0.01度セルで、セルは 1,113m × 902m、半径は 717m。この前提で隣接する円の
重なりを計算すると:

| 隣接方向 | 中心間距離 | 2円の共通面積 | 円面積に対する比 |
|---|---:|---:|---:|
| **東西** | 902m | 412,562 m² | **25.5%** |
| 南北 | 1,113m | 198,112 m² | 12.3% |
| 斜め | 1,433m | 40 m² | ≒0% |

`findOverlappingPairs` の既定閾値は `minFraction = 0.2`(`lib/grid/GridOverlapAnalysis.js:64`)。
**東西の隣接はこれを常に超える。** そして `findOverlapClusters` は Union-Find
(同94-119)なので、東西につながった1行がまるごと1クラスタになる。

ここから、ドキュメントの数字がそのまま説明できる:

- `lngSteps = round((140.12 − 139.90) / 0.01) = 22` → クラスタサイズ「22〜23マス」と一致
- 未検索の階層0セルは131行。131 ÷ 22 ≈ 6行 → クラスタ数「6個」と一致

つまり **「大きいグループ(22〜23マス、6個)」は、未検索のまま残っている階層0の東西6行**であって、
旧バグの産物ではない。`entrypoints/auditGridOverlap.js:99-107` の
`savableCalls = 関与セル数 − クラスタ数` は「1クラスタに1件残す」前提なので、
この6クラスタに適用すると **20km幅の1行を1つの717m円で見る**ことになり、その行の店をほぼ全部落とす。

ログ自体は「その代わり、重複していない残り部分の店を取りこぼす」と注記しているが、
`current-status` 側が「昔のバグで生まれた無駄」と書いていたため判断を誤りやすかった。

**`auditGridOverlap` は「正方格子で構造的に避けられない重複」と「旧0.6R方式の兄弟円の重複」を
区別していない。** 小さいグループ(2〜4マス、77個)のほうは旧方式の兄弟円由来という説明と
整合するが、この監査ツールの出力だけでは両者を切り分けられない。

### (B) 対象矩形が広すぎる ← 効果は最大、APIコストは0

`TARGET_AREA_BOUNDS`(`lib/grid/TargetArea.js:6`)は 35.77–35.94 × 139.90–140.12。
実距離で **19.8km × 18.9km = 376km²、柏市115km²の3.27倍**。
`docs/survey-findings-2026-09.md:84` の通り密度1位は松戸駅前(柏市外)で、
手賀沼・利根川・江戸川・農地も含む。374マスのうち柏市域にかかるのは概ね1/3。

`isWithinTargetArea`(`lib/grid/TargetArea.js:26-31`)は差し替え前提でコメントまで用意されているが、
**`entrypoints/generateGridList.js:59-69` はこの関数を呼ばず、矩形を直接二重ループしている。**
`isWithinTargetArea` の呼び出し元は `lib/grid/GridSubdivision.js:81` だけ。

→ **市域ポリゴン判定に差し替えても、それだけでは階層0のマスは1つも減らない。**
やるなら `generateGridList` の生成ループも `isWithinTargetArea` を通す必要がある。

なお水域の除外に外部データは要らない。調査で0件だった331マスが同じ役割を果たす
(OSMによる事前除外は的中率2.6%で却下済み、`docs/survey-findings-2026-09.md` 2-2)。
ただし上記(3)の通り、今後クロールするマスの0件情報は記録されない。

### (C) `spawnChildGrids` の範囲外チェックは実質発火しない

`lib/grid/GridSubdivision.js:75` の `margin = GRID_STEP`(0.01度)は階層によらず固定。
階層3の子セルは0.00125度なので、子セル8個ぶんの余裕という計算になる。

そもそも子セルの中心は必ず親矩形の内側にあり、親は必ず bounds 内にあるので、
**margin=0 でも通ってしまう。** `skipped > 0` のログ(同93-95)が、正常に生成された
グリッドから出ることはない。(B)でポリゴン判定に移行するなら、ここも合わせて見直しが要る。

### (D) 事前の密度反映がない(不均一グリッド化の余地)

全域を一律0.01度で切り、密なら事後に分割する(＝親コールを1回捨てる)方式になっている。
`調査(マス)` に638行の密度が既にあるので、**生成時点で密な場所は細かく、疎な場所は粗く**
切れば親コールが不要になる。1章(1)と同じ改修で同時に解ける。

### (E) 格子の形そのものを変える余地は限定的

| 案 | 円 / 担当領域 | 必要セル数の比 | 備考 |
|---|---:|---:|---|
| 現状(度で正方形) | 1.61倍 | 1.00 | 円の37.8%が担当外 |
| メートルで正方形(経度刻み0.01234度) | 1.571倍 | 0.98 | 改善2%、ほぼ無意味 |
| 六角格子 | 1.209倍 | **0.75** | 374→281マス |

六角格子は四分木分割ができず、セル中心が全てずれて進捗を引き継げない。
`docs/Overview.js` が既に「移行するなら別プロジェクトとして作り直す必要がある」と
結論づけている通りで、**格子の形に手を入れるのは費用対効果が悪い。**

## 4. 踏んではいけない地雷(今回追加ぶん)

### `auditGridOverlap` の「削減できるコール数」を額面通りに受け取らない

`savableCalls` は「1クラスタに1件だけ残す」という単純な前提の数字であり、
正方格子で構造的に避けられない東西重複(25.5%)もまとめて数えている。
大きいクラスタに適用すると広い範囲を1円で見ることになり、取りこぼしが出る。
→ 上記(A)

### ドキュメントの半径は700mと717mが混在していた

`generateGridList` が半径700mを決め打ちしていた時代の数字が、計算結果として残っている箇所があった
(`docs/Overview.js` の円面積。本PRで訂正)。
`docs/current-status-2026-09-20.md` が「700m→本当は717m」と直したのと同じズレ。
面積や比率を引用するときは、どちらの半径で計算された数字かを確認すること。

### 数値の再計算方法

本書の幾何の数字は以下で再現できる(APIコール0)。

```bash
node -e "const M=111320,lat=35.855,s=0.01;const dLat=M*s,dLng=M*Math.cos(lat*Math.PI/180)*s;const r=Math.ceil(Math.hypot(dLat/2,dLng/2));const L=(d)=>2*r*r*Math.acos(d/(2*r))-(d/2)*Math.sqrt(4*r*r-d*d);const A=Math.PI*r*r;console.log('半径',r,'/ 円',(A/1e6).toFixed(3)+'km2','/ 倍率',(A/(dLat*dLng)).toFixed(3),'/ 東西重複',(100*L(dLng)/A).toFixed(1)+'%','/ 南北',(100*L(dLat)/A).toFixed(1)+'%')"
```
