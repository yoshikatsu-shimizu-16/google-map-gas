# 全域調査の結果と次の一手（2026-09-20）

APIコールの無駄を削るため、実装を決め打ちせず **Pro枠で全域を実測** した。その結果と、
確定した設計方針、残っている作業をここにまとめる。

## 1. なぜ調査したか

### 発端

「APIコール数が多い」「無駄な重複がある」の2点が課題だった。2026-09-20 の実測
（`crawlAllGrids` 15マス / 103コール）で内訳はこうだった。

| 内訳 | コール数 | 割合 |
|---|---|---|
| グループA | 15 | 15% |
| グループB/C/D | 36 | 35% |
| **タイプ再分割** | **52** | **50%** |

**85%が「どう割れば20件に収まるか」の試行錯誤**で、それが営業データと同じ
Enterprise枠（1,000/月）を食い合っていた。

### 枠を分けた

Places API の無料枠は課金SKUごとに別勘定で、SKUは fieldMask の中身で決まる。

| SKU | 無料枠/月 | 用途 | fieldMask |
|---|---|---|---|
| **Pro** | **5,000** | 調査 | `PLACE_SURVEY_FIELD_MASK` |
| Enterprise | 1,000 | 営業データの収穫 | `PLACE_SEARCH_FIELD_MASK` |

調査に必要な `places.types` は Pro段に含まれる（[公式のフィールド一覧](https://developers.google.com/maps/documentation/places/web-service/nearby-search)で確認済み）。
評価もHPも要らないので、**試行錯誤を5倍の枠に逃がせた**。

## 2. 測った結果

Pro枠 **3,370 / 5,000** を使用。**Enterprise枠は1コールも消費していない**（410のまま）。

### 2-1. 傘型プローブは100%成立した

`includedTypes` は `primaryType` ではなく `types` 配列全体にマッチする。つまり
`restaurant` 1種でラーメン屋も寿司屋も返る。これが成立するなら166種の列挙は不要になる。

| 検証 | 母集団 | 結果 |
|---|---|---|
| API差分（`compareProbeSetWithTypeGroups`） | 60件 | 取りこぼし **0件** |
| シート実測（`surveyAllCells`） | **7,027件** | 被覆率 **100.0%** |

**166種のカタログも A/B/C/D の4グループも、通常の探索には不要。**

最小被覆集合（貪欲法、7,027件に対して）:

```
1. restaurant       +5310 (累計 75.6%)
2. cafe              +692 (85.4%)
3. bakery            +398 (91.1%)
4. confectionery     +251 (94.6%)
5. bar               +160 (96.9%)
...
17. chocolate_factory  +1 (100.0%)
```

**17種で100%、上位5種で96.9%。** 現行の36種プローブ集合すら過剰だった。

カタログ166種のうち、**実在が確認できたのは104種、62種は1度も出現しない**。

### 2-2. OpenStreetMap による密度推定は使えなかった

外部データで空マスを事前に除外できないか試したが、**的中率2.6%**で却下。

```
OSMが0件と判定した78マスのうち
  Googleでも見つからなかった:  2マス
  Googleでは店が見つかった  : 76マス
```

OSM の対象エリア内の飲食系POIは2,515件。Googleは部分的なクロールだけで3,944件。
**日本の飲食店データはOSMの網羅性が桁違いに低い。**

判定はAPIコール0で行った（既にクロール済みのマスの結果と突き合わせた）。
実際に76コール使う前に却下できた。

関連コードは残してある（`tools/buildDensityMap.js` / `npm run density`）。
密集の**相対的な**分布は読めるので、対象エリアの妥当性を見るのには使える
（1位のグリッド23=201件は**松戸駅前**で柏市外）。

### 2-3. 全域の密度（`surveyAllCells`、638マス / 638コール）

```
0件(探索不要)           :  64マス (10.0%)
1〜4件                  : 132マス (20.7%)
5〜19件(1コールで足りる) : 222マス (34.8%)
20件以上(要分割)        : 220マス (34.5%)
```

### 2-4. 飽和マスの分割（`surveySaturatedCells`、2,668コール）

飽和マスを4分割し、20件未満になるまで繰り返した。階層6（半径約11m）で打ち切り。

| 階層 | 半径 | マス数 | 0件 | 1〜19件 | 飽和 |
|---|---|---|---|---|---|
| 1 | 359m | 468 | 39 | 346 | 83 |
| 2 | 179m | 352 | 39 | 233 | 80 |
| 3 | 90m | 320 | 25 | 232 | 63 |
| 4 | 45m | 644 | 51 | 470 | 123 |
| 5 | 22m | 492 | 64 | 330 | 98 |
| 6 | 11m | 392 | 49 | 278 | **65** |

**飽和率はどの階層でも18〜23%で収束しない。** 半径を縮めても同じビルの中の店は
分離できないため。階層6で飽和したままの**65マス**は、空間分割では原理的に解けない。

> 階層の数字が飛んで見えるのは、`グリッド一覧` に階層0のマスと過去のクロールが
> 作った階層1〜3の子マスが混在しているため。階層3のマスを割れば子は階層4になる。

### 2-5. 4分割 vs タイプ分割

| 方式 | 飽和マス1つあたり | 解決率 |
|---|---|---|
| タイプ分割（現行） | 4 + 7 = **11コール** | 過去の実測で6マス中4マスが未解決 |
| **4分割** | 1 + 4 = **5コール** | **50.9%** |

**通常の飽和マスは4分割のほうが安い。タイプ分割が要るのは階層6で残った65マスだけ。**

## 3. 確定した設計

### 収穫（Enterprise枠）で叩くべきマス

調査で「1〜19件」と分かっているマス＝木構造の葉だけを叩けばよい。

| 区分 | マス数 | コール数 |
|---|---|---|
| `調査(マス)` の1〜19件 | 354 | 354 |
| `調査(分割マス)` の1〜19件 | 1,889 | 1,889 |
| 0件（探索不要） | 331 | **0** |
| 階層6で飽和（タイプ分割が必要） | 65 | 約715（11コール/マス） |
| | | **合計 約2,960** |

**Enterprise枠 1,000/月 → 完走まで約3.0ヶ月。**

### 期待値の訂正

調査の途中で「1.5ヶ月」「67%削減」と見積もったが、**いずれも楽観的すぎた**。

理由は単純で、**分割するほどマスの数が増える**から。25件のマスを4分割すると、
1コールで取れなかったものが4コールになる。理論下限（総店舗数÷20）に対して、
疎なマスが多いぶん3〜4倍かかる。

ただし現行方式は同じ木構造を辿りながら1マス4〜11コール払うので、完走には
2万コール規模になる。**約2,960は桁が1つ違う。**

## 4. 次の一手

### 4-1. 収穫ロジックの実装（本命）

`crawlAllGrids` を「調査結果の葉を1マス1コールで回る」方式に置き換える。

- 入力: `調査(マス)` と `調査(分割マス)` の「1〜19件」の行
- 各マスを `PLACE_SEARCH_FIELD_MASK`（Enterprise段）+ 傘型プローブ集合で1コール
- 出力: 従来どおり `全飲食店データ`
- 進捗管理: どのマスを収穫済みかを記録し、中断・再開できること

これに伴い**消せるもの**（コード量が減る）:

| 現在 | 置き換え後 |
|---|---|
| `PlaceTypeCatalog.js`（166種の手書きカタログ） | 階層6の65マス用にのみ残す |
| `TypeGroupCellSearch.js`（4グループ + 7分割） | 同上（通常経路からは外れる） |
| `ProbeFirstCellSearch.js` + `SearchStrategyMode.js` | 1本に統合し、切替フラグを撤去 |
| `GridSubdivision.js` の事後分割 | 調査結果で事前に確定済み |

### 4-2. 階層6で飽和した65マスの扱い

1棟に20店舗以上入っているケース。`restaurant` を具体的な種類に割るしかない。
**166種カタログが最後にここで効く。** 先に Pro枠でタイプ分割の効き目を測ってから
実装するのが安全（Pro枠は約1,600残っている）。

### 4-3. 対象エリアの見直し（未着手）

対象矩形は **376km²、柏市（115km²）の3.3倍**。密集上位マスには松戸駅前・新松戸が
柏駅と同格で入っている。`isWithinTargetArea` の差し替えだけで絞れる（APIコール0）が、
**どこまでを対象にするかは人間の判断が要る**ため保留中。

地図で確認する方法は README にはないので再掲:
[geojson.io](https://geojson.io) に以下を貼ると現在の範囲が見える。


## 5. 踏んではいけない地雷

調査の過程で実際に踏んだ、または踏みかけたもの。

### Pro段のデータを `全飲食店データ` に書かない

Pro段には `rating` も `websiteUri` も無い。書き込むと評価とHPが空の行ができ、
**Place ID の重複除去で本番クロールが二度とその店の営業データを取りに行かなくなる。**
`compareProbeSetWithTypeGroups` は旧実装（Enterprise段）で書き込んでいたため、
段を下げる際に書き込みを廃止した。

### 自前のカウンタはGCPプロジェクトを区別しない

`MONTHLY_API_CALL_COUNT` はスクリプト単位。APIキーを別プロジェクトに差し替えても
カウントは引き継がれ、**キーを替えただけでは上限に達した状態は解消されない。**

### GAS から Overpass には到達できない

`UrlFetchApp` から `overpass-api.de` は `Address unavailable` になる。共用サーバーが
データセンターからのアクセスを弾いていると思われる。OSM の取得はローカルで行い、
結果を `lib/survey/EmptyCellPrediction.js` として持ち込む構成にした。

### GCPの割り当て画面の「使用量」は遅れる

数時間の集計遅れがあり、実際に使っていても0のまま表示される。
スクリプト側の `checkMonthlyApiUsage` のほうが正確。

### 日次割り当てと無料枠は別物

`SearchNearbyRequest per day`（GCPのレート制限、上げても無料）と
無料枠（SKUごとの月間、上げられない）は独立。混同しないこと。

## 6. 調査に使ったもの

| エントリーポイント | 用途 | コスト |
|---|---|---|
| `surveyAllCells` | 全マスの密度とタイプを測る | 1マス1コール（Pro） |
| `surveySaturatedCells` | 飽和マスを4分割。実行のたびに1段深く掘る | 親1つ4コール（Pro） |
| `compareProbeSetWithTypeGroups` | 傘型プローブと4グループの差分検証 | 1マス最大5コール（Pro） |
| `auditProbeSetCoverage` | シート実測から被覆率と最小被覆集合 | **0コール** |
| `surveyEmptyCells` | OSMが0件と見たマスの実地確認（結果的に不要に） | 1マス1コール（Pro） |
| `checkMonthlyApiUsage` | SKU別の消費確認 | **0コール** |

全ての調査系は `SURVEY_MAX_CALLS` で上限を指定できる。**`0` にすると消費予定の
コール数を報告するだけで、Googleへのリクエストは1件も発生しない。**

出力シート:

- `調査(マス)` … マス単位の密度（グリッドIDごと）
- `調査(店)` … 店単位のタイプ実測（7,027件）
- `調査(分割マス)` … 分割したマスの密度（セルIDはパス形式 `301-北東-南西`）
