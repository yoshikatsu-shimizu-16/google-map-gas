# 今どうなっているか(2026-09-20時点、更新版)

読み返す用のまとめ。技術の詳細は他のdocsに譲り、ここは「結論」だけ書く。

## 1. 本番は今どう動いているか

前提: この仕組みは、対象エリアの地図を方眼紙のように正方形のマスへ区切り、
マス1つずつについて「この範囲に飲食店は何がありますか」とGoogleに問い合わせて
いく作りになっている。問い合わせ1回を「1コール」と呼んでいる(1コールごとに
コストがかかる)。

- **何を検索するか(検索条件)**: 1マスにつき、**プレイスタイプ36種類の集合**で
  1回だけ問い合わせる。「プレイスタイプ」はGoogleの公式用語で、場所の種類を表す
  分類のこと([Table A](https://developers.google.com/maps/documentation/places/web-service/place-types?hl=ja#table-a)、
  例: `restaurant`, `cafe`)。以前は166種類を4つのグループに分けて何度も問い合わせて
  いたが、36種類だけで足りることが分かったため1回に統一した。
- **どこを検索するか(分割)**: Googleの検索は1回の問い合わせにつき**最大20件までしか
  返してこない**制限がある。あるマスに実際は20件を超える飲食店があると、1回の
  問い合わせでは取りこぼしが出る。その場合、**そのマス(正方形の区画)を田の字に
  4つの小さい区画へ切り分け、それぞれの区画に対してもう一度1回ずつ問い合わせ直す**
  (=4分割)。分割してもなお20件を超える区画があれば、その区画だけをさらに4分割する。
  この「分割してもまだ多ければまた分割する」は最大3段階まで自動で行い、3段階
  分割してもまだ20件を超える場合は、人間の確認に回す(`lib/grid/TargetArea.js`の
  `MAX_TIER = 3`)。
- **同時実行の防止**: `crawlAllGrids` は **同時に2つ動かない**ようになっている
  (排他制御、Issue #23・完了)。
- ここまでは実装・テスト・GASへの反映が完了していて、**次回のトリガー実行から
  そのまま効く**。何か操作する必要はない。

「マス(検索範囲)の一覧」を記録している「グリッド一覧」シート(638行、1行=1マス)を

- **半径のズレ(700m→本当は717m)**: 374行全部が対象。うち131行はまだ未検索なので直せる
- **重複している検索範囲**: 未検索の395行のうち347行(88%)が、他のどこかの行と探索範囲(円)が重なっている。
  ただし**この88%の大半は直せる無駄ではない**(下記「重複の内訳」を参照)

「探索範囲が重なっている」とは、本来別々の場所を見るはずのマス同士が、実際には
同じ場所を2回以上見てしまっている状態を指す。実害(二重にお金を払った)はまだ
出ていない。**今のまま普通にクロールを続けても、これまでと同じようにデータは
集まる。**

### 重複の内訳(2026-09-21 訂正)

> **以前ここに書いていた内容は誤りだった。** 「重なりはすべて昔のバグの名残」と
> 説明していたが、調べ直したところ**大きいグループは全く別の原因**だった。
> 詳細は `docs/api-call-waste-2026-09-21.md` 2章(A)。

2つのマスが重なっているだけの単純なケースもあれば、複数のマスが鎖のように
次々と繋がって、結果的に広い範囲でひとまとまりに重なっているケースもある。
「重なっているマス同士を1つのグループとしてまとめる」というのは、この鎖で
繋がったマスをひとまとめに数える、という意味。実際に数えると、グループの
大きさが2種類にはっきり分かれたが、**原因はそれぞれ違う**。

- **小さいグループ(2〜4マス、77個)**: 1つの場所を4分割したときにできる
  「兄弟」のマス同士が、そのままお互いに重なっているケース。これは昔の
  (今より不正確な)4分割のやり方の名残と考えられる
- **大きいグループ(22〜23マス、6個)**: **これはバグではなく、今の格子の作りから
  必ずこうなる。** 1マスは東西902m・南北1,113mの長方形で、それを漏れなく覆う円の
  半径は717m。すると**東西に隣り合うマスの円は必ず25.5%重なる**(南北は12.3%)。
  重複と見なす基準が20%なので、東西の隣同士は全部「重なっている」と判定され、
  鎖のように1行まるごとが1グループになる。実際、東西方向のマス数は22で
  グループの大きさと一致し、未検索のまま残っている行数(131)を22で割ると
  約6行でグループ数とも一致する

つまり大きいグループの正体は「未検索のまま残っている東西6行」であって、
**直せる無駄ではない**。正方形のマスを円で覆う以上、構造的に避けられない。

**やってはいけないこと**: `auditGridOverlap` は「各グループから1つだけ残せば
約○コール減らせる」と出すが、大きいグループにこれを適用すると**東西20kmの1行を
1つの717mの円で見る**ことになり、その行の店をほぼ全部取りこぼす。
この数字は小さいグループにしか当てはまらない。

小さいグループの整理は引き続き検討できる(下記4-2)。
